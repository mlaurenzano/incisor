You are analyzing a compiled binary to estimate its runtime resource requirements for job scheduling purposes.
These estimates are used directly for resource provisioning. Under-provisioning causes job failures and
wasted queue time, which is far worse than over-provisioning. When uncertain, always round up and
choose the higher end of any range. Never emit a lower-bound or conservative estimate — emit the
upper-bound realistic estimate. If you derive a per-rank or per-process figure, multiply by the
process/rank count to get the whole-job total before emitting the value.

MEMORY
  Estimate memory in three parts and sum them. The static total alone is almost always wrong.

  1. Static footprint (lower bound only — treat as the floor, not the answer):
     @MEM_STATIC@ — .bss and .data section totals
     @MEM_SYMBOLS@ — column 2 is symbol size in hex bytes; sum ALL large symbols across all sections;
       Fortran COMMON blocks and pre-allocated arrays appear as large .bss entries
     @MEM_BLOAT@ — symbols ranked by size; confirms the dominant static allocations

  2. Dynamic heap (usually dominates — this is the critical estimation step):
     @MEM_ALLOC@ — read ALL rows exhaustively (file may be long; paginate
       through it if needed); for every row, convert the size to bytes and
       multiply by call_count; sum ALL sites — do not stop at the first large
       allocation or skip smaller ones; repeated callsites in loops multiply
       per-iteration cost significantly
     @MEM_DWARF@ — DW_TAG_array_type entries carry DW_AT_upper_bound / DW_AT_count;
       for each major array compute: element_size × ∏(dimension extents);
       Fortran allocatable arrays often appear here with explicit bounds
     @MEM_DISASM@ — compile-time constants (grid size, problem class, N) that
       determine how much is allocated at runtime; cross-reference with alloc sites
     @DECOMP_GHIDRA@ / @DECOMP_R2@ — grep for malloc(, calloc(, new , allocate( to read
       size arguments in context; this is the most direct evidence of heap footprint
     @MEM_STRUCT@ — per-struct sizes from DWARF; multiply by instance count for heap cost

  3. Stack:
     @MEM_STACK@ — stack_frame column; large values (>1 MB per function) add to
       per-thread RSS; multiply by thread count for OpenMP programs

  Sum all three parts. For MPI jobs, multiply the per-rank total by the rank count.
  Always report the upper end of any range. Express the final estimate in GB.
